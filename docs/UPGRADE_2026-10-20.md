## 3. `ANDROID_PREFS_ROOT` / `ANDROID_USER_HOME` (brief §3)

**Root cause.** AGP's `AndroidLocationsBuildService` computes the Android
preferences folder (`.android`) from every source that is set —
`ANDROID_USER_HOME` (the folder itself, current), `ANDROID_PREFS_ROOT`
(its *parent*, deprecated), `ANDROID_SDK_HOME` (its parent, deprecated) —
and throws `AndroidLocationsException` ("Several environment variables
… contain different paths to the Android Preferences folder") when they
resolve to different folders. The classic trigger is
`ANDROID_PREFS_ROOT=$HOME/.android` copied from older docs (which describe
it as the `.android` path) alongside a correct `ANDROID_USER_HOME`.
Nothing is wrong with the SDK or `.android`; deleting either fixes nothing
and destroys AVDs/debug keys.

**Fix (minimal, persistent, no deletions).**
- `.vscode/settings.json` (new): `terminal.integrated.env.*` unsets
  `ANDROID_PREFS_ROOT` and `ANDROID_SDK_HOME` (`null`) and pins
  `ANDROID_USER_HOME=$HOME/.android` for Linux/macOS/Windows — so every
  *fresh* VS Code terminal has exactly one source of truth, with no shell
  profile edits. Open a new terminal to pick it up.
- `tools/check_android_env.sh` (new): read-only diagnostic that prints the
  resolved folder per variable, exits 1 with the exact fix when they
  conflict, warns (exit 0) when deprecated variables merely agree. Tested
  here: clean env → OK; synthetic conflict → exit 1 with correct diagnosis.
- `docs/RELEASE.md` §0/§7: prerequisite table updated and a troubleshooting
  row documents the same fix for non-VS-Code shells (`~/.bashrc`).
- In this sandbox both variables are unset, so the failure itself is
  **not reproducible here**; the fix is verified by the diagnostic script
  and by AGP's documented location rules, not by a Gradle run.

`title: 'All trackers',` in the same file. The checks themselves

### 4.4 gate_probe P-20 / P-22 glance version (regression introduced here → fixed)

## 8. Addendum — 2026-10-21: the Gradle problems-report warning

The first build on the matrix in §2 produced one entry in
`android/build/reports/problems/problems-report.html`:

```
Deprecated 'org.jetbrains.kotlin.android' plugin usage
  The 'org.jetbrains.kotlin.android' plugin in project ':app' is no longer
  required for Kotlin support since AGP 9.0.
  Solution: Remove both android.builtInKotlin=true and android.newDsl=false
  from gradle.properties, then migrate to built-in Kotlin.
```

**Mechanism, read from the Flutter 3.47.7 source rather than guessed.**
`FlutterPluginUtils.detectApplyingKotlinGradlePlugin` walks every subproject;
when `isBuiltInKotlinEnabled(...)` is false (it is, because
`android.builtInKotlin=false`) and a module has AGP but no KGP, it runs
`pluginManager.apply("kotlin-android")`. `:app`'s build file deliberately does
not apply KGP, so the Flutter plugin is what applies it there — and KGP 2.3+
reports that application as the deprecation above. There is no edit to this
repository that removes it while the opt-out is active; the two ways out are
migrating to built-in Kotlin or suppressing that one diagnostic.

**Why migrating was not done in this pass.** Both blockers below are verified,
and either one alone fails the build:

1. `health` 13.3.2's `android/build.gradle` still contains
   `apply plugin: 'kotlin-android'` unconditionally. Under built-in Kotlin,
   applying KGP is a configuration error; the build would fail at `:health`
   before compiling Dart. (Checked at 13.3.2. `flutter_local_notifications`
   22.3.2, by contrast, applies only `com.android.library` — the earlier note
   that both still applied KGP was wrong for that one.)
2. Flutter 3.47.7's `DependencyVersionChecker.checkKGPVersion` errors below
   KGP 2.2.20, while AGP 9.1's own compatibility table lists KGP 2.2.10 as both
   the minimum and the default — the failure in `flutter/flutter#192167`. The
   skip for built-in Kotlin is
   `flutter/flutter#192206`, merged into Flutter master on 2026-09-08, **after**
   the 3.47 branch: the 3.47.7 source still runs the check unconditionally.
   Pinning a newer KGP onto the build classpath would be the only workaround,
   and it is unverified — not something to bet a release build on.

**The change.** `android/gradle.properties` now carries

```properties
kotlin.suppressGradlePluginWarnings=DeprecatedKotlinAndroidPlugin
```

the diagnostic id AndroidX itself suppresses, scoped to that one warning. The
two `android.builtInKotlin=false` / `android.newDsl=false` deprecation messages
are deliberately left visible: they are the AGP 10 removal deadline, and hiding
them would remove the only recurring signal that this is temporary.

**Guards added with it.** `tools/release_gate.py` **P-52** ("the AGP 9 Kotlin
opt-out is coherent and stays suppressible") fails unless the two flags, the
`org.jetbrains.kotlin.android` version pin and the suppression move together, and
unless `:app` remains free of a direct `kotlin-android` application. Two probes
in `tools/gate_probe.py` remove the suppression and the new-DSL flag
respectively and require P-52 to fire.

**While in that check**: P-20's Kotlin/Compose version comparison had never been
able to fire — its regex required `version("…")` and the settings file writes
`version "…"`, so it compared nothing and passed. The regex now accepts both
forms, and a probe (`Compose compiler drifting from the Kotlin pin`) proves it.

**Removal condition (also in `tools/diagnose_build.sh` and
`docs/BUILD_TROUBLESHOOTING.md` §3).** Delete the suppression in the same change
that removes the two flags, once `health` ships a built-in-Kotlin release *and*
the build runs on a Flutter containing #192206. Nothing in that sentence is
satisfied by this repository alone.

**Verification.** Structural only: `tools/release_gate.py` → 52 checks, 0
problems; `tools/gate_probe.py` → every probe fires and the tree restores clean.
No Gradle run was possible here (no JDK/Android SDK, `dl.google.com`,
`maven.google.com`, `repo.maven.apache.org` and `pub.dev` all unreachable), so
whether the suppression removes the entry from the report is **NOT RUN** — the
first CI build on this change is the proof.
