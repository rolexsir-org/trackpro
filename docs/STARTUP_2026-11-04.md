# Blank screen — root cause and repair (2026-11-04)

Branch: `arena/7d9c99b4-trackpro` · Base: `main@5784052` · Working tree at the start of this
pass: **clean** (`git status --porcelain` empty), no uncommitted user changes to preserve.

This file answers one question: *the release APK launches and then shows a blank screen — why,
and what changed?* It separates what was **proved** from what could **not** be executed in this
checkout, because this repository has never had a Flutter, Dart, Java or Android toolchain
(see `PUBLISHING_GAPS.md` §1 and `TEST_RESULTS.md` §4). Nothing below claims a build or a device
run that did not happen.

---

## 1. Confirmed root cause

**The application rendered no widget tree until every initialization step had completed, and had
no state to express "starting" or "failed".** The whole start-up chain sat between process start
and `runApp()`, in `lib/main.dart` (as shipped at `5784052`):

```dart
await notifications.init();   // platform channel: timezone db, plugin init, 4 channels
await state.load();           // DB open + migration + catalog + hydrate + settings
                              //   + commitment hydrate + legacy import
                              //   + FocusRepository.hydrate() + recoverFocus()
                              //   + syncFocusSchedules()  ← schedules N notifications
                              //   + refreshReminders()    ← another plugin round-trip
if (kReleaseMode) { AppEnvironment.validate(); }
WidgetsBinding.instance.addObserver(lifecycle);
runApp(TrackApp(state: state));   // ← first frame is only possible here
```

Three consequences follow directly from that shape, and all three are the same defect:

1. **A throw anywhere in the chain produces a permanently blank window.** `main()` has no
   handler, so the exception ends the start-up isolate before any frame is scheduled. Android
   keeps the activity on `@style/LaunchTheme` (`android:windowBackground` =
   `@drawable/launch_background` = a flat `#F2F2F7` rectangle on light, black on dark) for ever.
   That rectangle *is* the blank screen — not a white page inside the app, but the launcher
   splash with nothing ever painted over it.
2. **A hang anywhere in the chain does the same, silently.** Every awaited step crosses into
   Android (notification plugin, `track/focus` channel, `track/screen_time`, Health Connect).
   None of them had a timeout, so a wedged channel, a suspended permission dialog or a slow
   OEM Health Connect binding left the app on that rectangle with no bound and no message.
3. **Nothing distinguished "loaded" from "finished loading".** `runApp` was last only by
   convention. There was no `isLoaded`, so no code could tell that the app was about to render
   five screens' worth of charts, rings and streaks from a projection that had not hydrated.
   A load that silently returned early was indistinguishable from one that worked.

The optional integrations were the most likely trigger, and that is the part the code made
impossible to survive: `AppState.load()` awaited `recoverFocus()`, `syncFocusSchedules()` and
`refreshReminders()` — three native round-trips — in the same block as the database. A device
without Usage Access, without `POST_NOTIFICATIONS`, without Health Connect, or with an OEM that
stalls a channel is a **normal** device, and on all of them a single platform error aborted the
whole load, and therefore the whole launch.

This also explains the reported shape ("launches, does some initial work, then blank"): the
launcher chrome and the splash window are visible while the chain runs, and the point at which
the window stops being a splash and should become the app is exactly the point that never
arrived.

### The native side was checked and is not the cause

`MainActivity.kt` (channels registered in `configureFlutterEngine`, `FlutterFragmentActivity`),
the merged manifest (every component resolves — gate P-18), the launch/normal themes, the R8
keep rules (`proguard-rules.pro` keeps the widget receiver, both receivers, the focus service
and overlay, `flutterlocalnotifications`, `billingclient` — gates P-21/P-22), and the release
signing fallback are all intact. No release-only native defect was found, and **no security,
billing, R8 or ProGuard setting was touched** by this change.

## 2. What changed (exact files)

| File | Change |
|---|---|
| `lib/state/app_startup.dart` | **New.** `StartupPhase` (idle/running/ready/failed), `StartupIssue`, and `AppStartup`: the sequence as a state machine. Idempotent `start()`, explicit `retry()`, a bounded essential stage, a "ready means `isLoaded`" rule, and a background pass that records its own failures. |
| `lib/screens/startup_gate.dart` | **New.** `StartupGate` — the widget `MaterialApp.home` now builds. Renders the loading state, the failure state with **Try again**, and only mounts `HomeShell` when the phase is `ready`. |
| `lib/main.dart` | `runApp()` no longer sits behind initialization: the app builds first, and the awaited chain became `AppStartup.essential` (notifications init + `state.load()`, order preserved — gate P-26) with the billing/reminder/health/screen-time work moved to `AppStartup.background`. Added `installErrorRecording()`, which routes `FlutterError.onError` and `PlatformDispatcher.onError` into the same diagnostics list instead of ending at `debugPrint`. The two silent `catch (_) {}` blocks around Health Connect and screen time now record what failed. |
| `lib/state/app_state.dart` | `load()` is now idempotent and retryable (`_loaded`, `_loading`); the essential stages throw, the optional stages (`Focus Lock`, `Reminders`, `Health Connect`, `Usage access`, `Insights`) are bounded by `optionalStageTimeout` and recorded in `startupIssues`; added `isLoaded` / `recordStartupIssue()`; `onResumed()` returns early until the load has finished. |
| `lib/screens/settings_screen.dart` | New **Diagnostics** section listing recorded start-up problems. The app's own main.dart already promised "Settings → Diagnostics shows the same list"; there was no such surface. |
| `lib/util/format.dart` | `shortErrorText()` — one bounded line from an error, so a diagnostics row names the failing layer instead of saying "something went wrong". |
| `tools/gate_probe.py` | Two probe anchors updated (P-01, P-26) because the lines they edit legitimately moved. Both probes still make their defect real; the full probe suite was re-run (§4). |
| `test/startup_test.dart` | **New.** Regression tests for this failure (§3). |

**Not changed:** the Drift schema, `schemaVersion` (4) and every migration; the repositories;
`marketplace`/Provider wiring (`ChangeNotifierProvider<AppState>.value` still lives in
`lib/main.dart`, gate P-23); Google Play Billing and its server-side verification, including the
fail-closed `Entitlement.active` rule and the acknowledgement-before-verification order;
Focus Lock, Health Connect, Usage Access, notifications, the widget, permissions, and the whole
Android/release configuration.

### Ordering that had to be preserved

`notifications.init()` **before** `state.load()`: `load()` re-arms reminders, and every
`NotificationService` method returns early until `init()` has run. With the order reversed, a
cold start left the user's *scheduled focus sessions* unarmed until they edited one — silently
no reminder after a reboot or update. `tools/release_gate.py` P-26 pins that order textually and
its probe still fires (§4). Focus Lock recovery (`_restoreFocusLock`: `hydrate` → `recoverFocus`
→ `syncFocusSchedules`) is unchanged in content and still runs on every launch; it is now bounded
and recorded instead of fatal.

## 3. Tests added (`test/startup_test.dart`)

All eight fail on the old code by construction: there was no phase to assert on, no gate to
render, and no record a failure could be found in.

| Test | What it pins |
|---|---|
| an essential failure is recorded and the app is not marked ready | `StartupPhase.failed`, the detail is in `startupIssues`, `isLoaded` stays false |
| a stage that completes without loading the database is a failure, not a success | the "ready means loaded" rule (the old code could mark a load "finished" that never opened anything) |
| a wedged essential stage times out into a retryable failure | the bound; and that completing the wedged future afterwards changes nothing |
| starting twice runs the sequence once | no duplicate bootstrap / duplicate listeners |
| a background integration that fails costs the feature, not the launch | phase is still `ready`, the failure is recorded |
| a fresh install has the catalogue and no invented history | first-launch path unchanged (no fabricated rows) |
| a second load joins the first instead of bootstrapping again | idempotence, catalogue written once |
| an existing install keeps its records across a restart | **existing data** survives a cold start (write, then load a second `AppState` over the same database) |
| a database that cannot be read fails the load instead of half-loading | essential failure is not swallowed |
| the first frame is the start-up screen, never the dashboard | widget test: first frame is the start-up screen; a "finished" stage that loaded nothing lands on the failure screen |
| a failed start-up explains itself and recovers on retry | widget test: reason + **Try again**, retry reaches `ready` and mounts `HomeShell` |
| once loaded, the real interface and first-launch onboarding render | widget test on a phone-shaped surface: `HomeShell` + onboarding as the first screen of a fresh install |

## 5. Remaining defects / blockers

1. **Nothing is compile-verified.** The new files and the edited ones have never been through
   `flutter analyze`; a first analyzer run should be expected to surface style or type issues,
   and none of them should be dismissed without a fix. This is the repository's standing
   blocker (§4), not a new one.
2. **`dart format` has not been run.** If CI's format gate disagrees with the hand formatting,
   the fix is `dart format`, not a code review.
3. **The APK still has to be built and installed once.** The repair makes a failed or wedged
   initialization *visible and retryable*; it does not by itself fix a database that is genuinely
   corrupt. If the first device run lands on the failure screen, the detail line now names the
   layer that refused — that is the diagnostic the old build never produced.
4. **`docs/TEST_RESULTS.md` and `docs/PUBLISHING_GAPS.md` were not rewritten.** They are dated
   audits of an earlier pass; this file supersedes nothing in them and is the record for this
   change.
